# Автопубликация без реакции редактора

В 12:00 UTC сегодняшний ежедневный готовый пост автоматически отправляется
одним фото с тем же форматированным текстом в `CHANNEL_PROD_ID` и
`CHANNEL_PROD_VIP_ID`, если ни один редактор не нажал «В тест», «Изменить»
или «Отклонить». Доставка на проверку должна быть подтверждена до 12:00 UTC.
Опоздавшие, недоставленные, старые и технические черновики не публикуются.

По согласованию с владельцем прежнее ручное поведение сохранено: «В тест»
только одобряет, затем администратор может нажать «Опубликовать в тест»
для прежнего `TELEGRAM_CHANNEL_ID`. Это не запускает отправку в два новых канала.
Любая из трёх кнопок отменяет автопубликацию для всего выпуска, включая
новые версии после доработки. Нажатие «Изменить» записывается как human comment
в `review_actions` сразу, до ввода замечаний; `/cancel` и рестарт запись не стирают.
Нажатие неавторизованным пользователем решения не меняет.

`daily_auto_publications` (миграция 020) фиксирует один план на UTC-день,
точный generated_post и два получателя. Результат каждого канала хранится
в `publication_attempts`. Автоматическое разрешение не выдаётся за human approve.
Блокировки post/batch общие с ручными решениями; после получения блокировки
повторно проверяются human actions, включая одновременно записанный comment.
Старые review-кнопки после claim удаляются по возможности; в любом случае
проверка БД запрещает позднее изменение уже публикуемого поста.

До claim проверяются текст, PNG и SHA-256. Длина и форматирование сохраняют
существующий контракт. Отправка использует существующий формат
[Telegram sendPhoto](https://core.telegram.org/bots/api#sendphoto).
Обе отправки независимы. Если первый канал недоступен, второй всё равно
обрабатывается. Выпуск получает `published` только после подтверждения обоих.
При частичном результате batch остаётся `publishing` с диагностикой.
`published`, `unknown` и `started` блокируют повтор для своего канала.
При потерянном ответе sendPhoto фиксируется `unknown`, даже без message_id;
автоматический повтор небезопасен и запрещён до ручной сверки.
При прерывании процесса `started` также требует сверки. Явный отказ Telegram
даёт `failed`; повторный ручной запуск может отправить только этот канал.
Существующий `reconcile_publication_attempt.py` рассчитан на один канал:
для этих попыток его не использовать, пока состояние обоих каналов не сверено.

Новый systemd timer `top3-news-auto-publish.timer`: один запуск в 12:00 UTC,
`Persistent=false`, без догоняющей публикации после перезапуска сервера.
В момент 12:00 начинается отправка; доставка в два канала последовательна
и зависит от Telegram/сети. Старое расписание генерации 07:30/07:45/08:00
не меняется. Новые платные OpenAI-вызовы не выполняются.

Конфигурация: `CHANNEL_PROD_ID`, `CHANNEL_PROD_VIP_ID` и
`AUTO_PUBLICATION_ENABLED=true`; по умолчанию функция выключена.
ID должны быть разными и начинаться с `-100`. Секреты `.env` не включаются в Git.
Для установки: подготовить только два ID в приватном JSON на cloud-001,
запустить `scripts/rollout_auto_publication.sh <проверенный SHA>` с интерактивным
sudo. Скрипт делает backup `.env`, применяет 020 через stdin, обновляет код
из GitHub, сохраняет старый ручной канал, проверяет права бота без отправки,
устанавливает timer и перезапускает бота. Dry-run читает БД и файлы,
не создаёт план/попытки и не обращается к Telegram.

Проверка: `scripts.test_auto_publication` требует `APP_ENV=testing`,
`DB_PORT=55432`, `DB_NAME=top3_auto_test`; запуск только на cloud-001
в отдельной PostgreSQL. Telegram подменён fake, OpenAI не используется.
Проверяются deadline, все три кнопки, старые версии, пропущенная доставка,
частичный успех, неизвестный исход, сбой фиксации, повтор, параллельные запуски
и обе стороны гонки с кнопкой. Отдельно проверяется реальный handler «Изменить».
