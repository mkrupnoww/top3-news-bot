# Повторы между выпусками и реальная замена новости

Причина инцидента 25 октября 2026: выпуск 24 октября содержал Deadline
`news_id=8257` о показе первых 17 минут Cliff Booth на AFI Fest, а следующий
выпуск — THR `news_id=8262` о том же показе. Прежний SQL исключал только
опубликованный `news_id`. Внутренние story clusters не сравнивались с историей.
Замечание «Замени третью новость» запускало regenerate_text по той же тройке.

## Проверка опубликованной истории

Перед event ranking читаются фактически опубликованные выпуски за предыдущие
семь UTC-дней: финальный опубликованный текст и исходные факты трёх новостей.
Учитывается также подтверждённая отправка в один канал при незавершённом втором.
Тестовые/отклонённые/ожидающие черновики и сегодняшний выпуск не являются историей.
Проверяется каждый кандидат, не только первоначальная тройка: запрет распространяется
на все комбинации и замены. Суточное окно самих кандидатов не расширяется.

Промпт v8 / evaluator v11 отличает повтор факта от существенного развития:
другое издание о том же показе — дубль; новые кассовые цифры Clayface после
предпоказов — новое развитие. Совпадение названия фильма/человека/кластера не
является достаточной причиной исключения. Исторические материалы считаются
справочными данными, а не инструкциями.

Ответ содержит обязательное nullable-поле `duplicate_of_published_news_id`.
Программа проверяет ссылку на переданную историю и принудительно устанавливает
`Q=0` для отмеченного дубля независимо от оценки модели. Существующая формула
не возвращает такие события при insufficient-TOP3 fallback. Все публикации
сохраняются в events/members для покрытия входа, а причина отражается в q_reason.
Решение о смысловом совпадении принимает модель; это не математическая гарантия
отсутствия любых повторов. Объяснение и ссылка сохраняются для проверки.

История входит в exact input/request key и background snapshot. Recovery
использует исходную историю, а не меняющийся набор публикаций. Старые snapshots
без истории остаются читаемыми, но версии v11/v8 отделяют новые запросы.
Новых отдельных ежедневных вызовов модели нет: история передаётся существующему
ранжированию. Строгая JSON-схема следует [OpenAI Docs](https://developers.openai.com/api/docs/guides/structured-outputs).

## Замена по замечанию

После «Изменить» можно написать «Замени третью новость» или «Замени новость №3».
Указанные инфоповоды исключаются целиком со всеми участниками, в том числе
другими источниками того же события. Из сохранённого ranking выбирается другая
комбинация с сохранением не затронутых новостей. Порядок выбранной комбинации
остаётся порядком ranking; повторное ранжирование не выполняется.
Ранее отвергнутые инфоповоды наследуются последующими заменами и не возвращаются.
Номер конкретной новости не угадывается: неоднозначное замечание вызывает
запрос номера, без API-вызова. Обычные правки формулировок/дат остаются в старом
regenerate_text pipeline и сохраняют состав.

Миграция 021 добавляет `editorial_replacement_requests`. Один review_action
фиксирует один план, source IDs, exclusions, выбранную combination и новые
batch/post. Session advisory lock не допускает параллельную замену одного запроса.
Используются существующие text/self-review и image reservations, usage и cost.
При восстановлении готовые этапы не генерируются повторно; неопределённый
незавершённый платный запрос не повторяется автоматически.

Новая подборка скрыта флагом `editorial_replacement_pending` до готовности текста
и нового PNG. Старый batch не изменяется до атомарной активации нового.
После успеха старый batch/post становятся superseded, новый ожидает ручной
проверки через `/review`. Ручная реакция наследуется новым batch и отменяет
автопубликацию. Новая картинка соответствует новой тройке; старая не копируется.
При отсутствии альтернативы исходный черновик возвращается в review-очередь,
а запись реакции сохраняется как human comment. Ошибки не превращаются
в незаметное перефразирование прежней новости.

Активный daily workflow сохраняет исходный завершённый snapshot; связь нового
ручного выпуска хранится в replacement plan/metadata. Ручная замена не запускает
повторную доставку или автопубликацию daily workflow. Уже опубликованные выпуски
не переписываются.

## Проверка и установка

Разработка на cloud-002 → GitHub → проверки только cloud-001.
`scripts.test_published_news_semantics` проверяет контракт истории, hard veto,
полное покрытие, strict JSON, восстановление snapshot и неоднозначные замечания.
`scripts.test_editorial_replacement` запускает настоящие text/image reservations
на копии production PostgreSQL 55432 (`APP_ENV=testing`, `top3_history_test`)
с fake OpenAI, без Telegram. Проверяются реальные batch_items/new PNG, ошибки,
рестарты, двойные запросы, параллельные вызовы, отсутствие замены, старый revision
и направление замечания через настоящий Telegram handler.

`scripts.probe_published_history --paid --output-dir <новый каталог>` — один
диагностический POST для трёх зафиксированных кандидатов инцидента, без repair,
retry, публикаций и записей в production-БД. Бюджетный ledger ограничен $1,
директория не может повторно использоваться. Запуск требует согласованного бюджета.

`scripts/rollout_semantic_replacement.sh <проверенный SHA>` применяет 021 через
stdin, обновляет код из GitHub, перезапускает бота и проверяет версии/таблицу.
Модели, секреты, имена кнопок и расписание не меняются. Для systemd/DDL требуется
интерактивный sudo. Скрипт установки платных вызовов не делает.

Проверка модели 2026-10-25: ровно один POST, accounted cost $0.03788850.
На реальных данных `8262` (THR о Cliff Booth) сопоставлен опубликованному `8257`
(Deadline); `8269` (новые сборы Clayface) и `8285` (SAG-AFTRA) получили null.
Точный запрос, ответ и ledger находятся на cloud-001 в приватном каталоге
`/tmp/top3-history-semantic-probe-20261025`. Публикаций и записей в production-БД
этот probe не выполняет. Это подтверждение конкретных примеров, не обещание
безошибочной семантической классификации любых будущих материалов.
